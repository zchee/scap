# Phase 4b — the mtime-validated repository index (AC-5)

Measurement record for the Phase-4b gate (plan §6 Phase 4b, ledger `#24b`).
The waves under test are `c15a085` `feat(index): add mtime-validated
repository index` and `15a2458` `test(index): mutation matrix against a fresh
walk`.

Every timed row in this document was taken by `scripts/bench-quiet.sh` on a
machine the D-1a gate admitted on its own. `SCAP_BENCH_FORCE` was never set,
`SCAP_BENCH_ALLOW_FLAGS` was never set. One completed group was discarded for
failing the closing gate; section [Refusals](#refusals-and-discards) lists
every refusal and that discard, with its numbers.

**AC-5 was restated by user ruling on 2026-08-30, and this document reports
both forms.** The criterion is now a **benefit ratio** between two rows taken
in the same group — warm cached `list` against `--no-cache` on a′ — bounded at
**0.60 on wall** and **0.35 on CPU**, and it is **MET**. The frozen absolute
bounds (5.09 ms wall, 6.58 ms CPU) are exceeded in every window and are
recorded **unattainable by construction**, with the arithmetic below; they are
reported beside the ratios and never gated alone, the same treatment deviation
D-9 gave the stale a+b absolutes.

Authority for that restatement is split and recorded as such: the ratio
**form** is the user's ruling; the two **multipliers** are **lead-proposed
from group 1's margins** (0.5345 wall, 0.2724 CPU), which were the only paired
figures in existence when the bounds were set. Group 5 was measured
afterwards, and it matters for reading the CPU bound that it landed much
nearer to it — see the note under the verdict.

## Pre-measurement checks

Both checks the review lane required were run before any timed row, and both
came back clean.

**Cache directory.** Resolved the way `src/index.rs` resolves it
(`cache_dir_from`: `$XDG_CACHE_HOME/scap`, falling back to `$HOME/.cache/scap`
when `XDG_CACHE_HOME` is unset, empty or relative). With
`XDG_CACHE_HOME=/Users/zchee/.cache` that is `/Users/zchee/.cache/scap`, which
did not exist — no index file written before `store_if_complete` existed could
have survived into these rows. It was `rm -rf`'d regardless before the first
cached run, and again before each group.

**Dropped subtrees.** The message `src/index.rs` logs when it declines to
write an index is `"<root>: a subtree was dropped; index left as it was"`.
Counting it under `SCAP_LOG=debug … list --cache`:

| Corpus | Root | `subtree was dropped` | repos | `dirs_read` | excluded | index entries |
| --- | --- | --- | --- | --- | --- | --- |
| a | `/Users/zchee/src` | **0** | 845 | 16,933 | 0 | 17,778 |
| a′ | a + exclusion | **0** | 845 | 1,198 | 1 | 2,043 |
| b | `/Users/zchee/go/src` | **0** | 981 | 2,608 | 0 | 3,589 |

No corpus carries an unreadable directory or a broken symlinked repository, so
no warm run is silently degenerating into a cold one.

**Corpus a and corpus a′ share one index file.** `Cache::path_for` names the
file from FNV-1a of the *root path*, and a′ is corpus a under an exclusion, so
both map to `index-6ae390cd4e4cd617.bin`. What separates them is the exclusion
list recorded inside the file, which `describes()` compares: an a run after an
a′ run (or the reverse) logs `index describes a different root; rebuilding`
and walks in full. Two consequences, both accounted for below — the warm rows
must be a′ runs back to back, which they are, and the "index size for a" and
"index size for a′" figures cannot exist on disk at the same time, so they are
reported one after the other rather than as a single listing.

## The bound's own denominator, re-measured

AC-5's bounds are not absolutes anyone chose. They are 1.25 × the W0.5 spike
row `w05-stat-aprime-n4`, which timed exactly the validation sweep this
feature implements — one `fstatat` per known path over a′'s 2,877 paths at
four threads — and read **4.066 ms wall / 5.259 ms CPU** on 2026-08-28.

A frozen figure cannot say whether a gap opened because the program got slower
or because the host did. That spike binary survives
(`.omc/spikes/w02-walker/target/release/spikestat`, sha256 `f511fe5a4650…`) and
so does its path dump (`docs/benchmarks/runs/20260828T104448Z-w05/aprime.dump`,
2,877 lines, sha256 `17d5a846ac65…`, untracked and therefore pinned by hash
here rather than committed), so the denominator was re-read in the same
windows as the numerator.

| Group | Spike wall (frozen 4.066) | Spike vs frozen | scap warm wall | Ratio (bound 1.25) | Spike CPU (frozen 5.259) | scap warm CPU | CPU ratio |
| --- | --- | --- | --- | --- | --- | --- | --- |
| g2 | 5.369 / 5.111 → 5.240 | 1.29× slow | 9.026 | **1.72** | 7.786 / 7.768 → 7.777 | 10.655 | **1.37** |
| g3 | 3.660 / 4.356 → 4.008 | **0.99× — reproduces** | 8.183 | **2.04** | 5.178 / 5.377 → 5.278 | 7.979 | **1.51** |

In group 3 the spike reproduces its frozen figure to within 1.5 % (0.9858×,
1.42 % below it), so that
window is genuinely comparable with the one W0.5 was measured in, and host
drift does not account for the gap: AC-5 exceeds its bound in ratio form too,
by a wider margin in the honest window than in the slow one.

Groups 1 and 2 sat in a window running about 1.29× slow. That is corroborated

1.29 factor. The Phase-3 re-gate reached the same conclusion about this host

## AC-5 — restated in benefit-ratio form

**Restated criterion (user ruling, 2026-08-30).** On a′, from paired rows
taken in the **same group**, warm cached `list` against `--no-cache`:

- wall ratio **≤ 0.60**
- CPU ratio **≤ 0.35** (user + sys)

The ratio form is the user's ruling. The two multipliers are **lead-proposed
from group 1's margins** — 0.5345 wall and 0.2724 CPU, the only paired figures
that existed when the bounds were set — and that split is recorded rather than
blurred.

The form is the same shape deviation D-9 gave AC-3, and for the same reason: a
ratio between two rows run beside each other in one window is immune to a host
that has moved, because whatever the machine is doing it is doing to both rows.

| Window | Warm wall | `--no-cache` wall | Wall ratio (≤ 0.60) | Warm CPU | `--no-cache` CPU | CPU ratio (≤ 0.35) |
| --- | --- | --- | --- | --- | --- | --- |
| g1 | 8.828 | 16.517 | **0.5345** | 9.251 | 33.967 | **0.2724** |
| g5 #1 | 6.605 | 11.923 | **0.5539** | 8.874 | 25.722 | **0.3450** |
| g5 #2 | 6.109 | 11.524 | **0.5301** | 8.561 | 25.135 | **0.3406** |
| g5 pooled | 6.357 | 11.723 | **0.5422** | 8.718 | 25.429 | **0.3428** |

**AC-5 wall ratio: MET.** **AC-5 CPU ratio: MET.** Two independent windows,
three independent pairs, every one inside both bounds.

**The CPU leg's margin is thin in the quieter window and that is disclosed,
not smoothed.** g5 pooled reads 0.3428 against 0.35 — 2.0 % of headroom —
where g1 reads 0.2724 with 22 % of headroom. The direction is systematic
rather than random: the quieter the host, the *worse* this ratio looks. The
bypassed row is dominated by system time (21–29 ms of the 25–34 ms total),
which is what a quiet machine speeds up most, so the denominator shrinks
faster than the numerator and the ratio rises. g5 is the quietest group taken
and therefore carries the tightest reading, which is the conservative one to
gate on. A future re-gate on an idle host should expect the CPU ratio near
0.34, not near 0.27.

### Why the absolutes are unattainable by construction

Group 3 measured the startup floor in the same window as the reference row,
which makes one piece of arithmetic available that the frozen bound could not
have taken into account.

`empty` is the W0.0 spike — a Rust `main` that returns immediately — so it is
process creation and dynamic linking and nothing else. Adding it to the
validation sweep gives the least any `scap` invocation could possibly cost on
this corpus while still doing the work AC-5 describes:

| Component (group 3) | Wall | CPU |
| --- | --- | --- |
| `empty` — process creation and linking | 2.516 | 1.406 |
| `w05_stat` — the validation sweep | 4.008 | 5.278 |
| **Floor: the two summed** | **6.523** | **6.684** |
| Frozen AC-5 absolute | 5.09 | 6.58 |

The floor exceeds both absolutes — by 1.43 ms on wall and 0.10 ms on CPU —
before scap resolves a root, reads any configuration, sorts, or prints 845
lines.

The mechanism is visible in the derivation: ⟨I_wall⟩ = 4.07 ms was measured by
a spike that takes its path list from a file on disk and pays no scap process
startup, and the 1.25× multiplier leaves 1.02 ms of wall for everything scap
does besides the sweep — while scap's measured startup floor alone is 2.52 ms.
No index implementation can close that difference, which is why the absolutes
are recorded unattainable rather than unmet.

### An observation on the remainder

For scale: scap's warm run in group 3 spends 8.183 − 6.523 = 1.66 ms above
that floor on root and configuration resolution, sorting and printing 845
lines. Phase 3 measured `root_env` — root resolution on its own — at 4.77 ms,
so 1.66 ms for the whole remainder is not an obviously bloated figure, and
nothing here points at a second optimisation target inside the warm path.

Recorded as an observation with its arithmetic. No bound is moved by it.

## Index file sizes

| Corpus | Entries | Index size |
| --- | --- | --- |
| a′ | 2,043 | 134,084 B |
| a | 17,778 | 2,123,187 B |
| b | 3,589 | 344,070 B |
| a and b together on disk | 21,367 | 2,467,257 B |
| Synthetic 25,120 directories (W4b.2, `tests/index.rs`) | 25,120 | 1,329,613 B |

The a and a′ figures were taken one after the other, not from a single
listing of the cache directory: the two corpora share one root path and so one
index file name, so writing either size to disk destroys the other, and only
the a-and-b pair can be observed together.

AC-5's size clause — "index ≤ 2 MB for 25 k directories" — is met on the row
it names: the synthetic 25,120-directory tree encodes to 1,329,613 B, about
two thirds of the allowance.

Recording the observation ledger `#24` raised, without moving the bound: real
corpus a encodes to 2,123,187 B at 17,778 entries, over 2 MB at fewer than
18 k directories. Real `~/src` paths average 119 B per entry against 53 B in
the synthetic tree (and 66 B in a′), so the ordering the clause implies —
more directories means a larger index — does not hold across trees of
different path depth. The quantity the file size actually tracks is encoded
path bytes, not directory count. Whether AC-5's clause should be restated in
those terms is the user's call.

### Two groups discarded on the closing gate

The closing-gate rule discards a completed group whose closing sample fails
CPU idle >= 85 % or busiest process <= 15 %. It fired twice, and both
discarded directories were moved out of the repository to
`/tmp/p4b-discarded/` with a `DISCARDED` file recording why.

**`20260829T210556Z-p4b`** — closing sample idle 86.65 %, **busiest process
47.0 %**. The start gate admitted it and all four rows completed. It was the
most favourable window taken, and its numbers are recorded here so that the
discard cannot be mistaken for a number that was quietly dropped: wall ratios
**0.529** and **0.535**, CPU ratios **0.271** and **0.272** — comfortably
inside both restated bounds, better than the group that replaced it. It was
discarded anyway. The closing-gate rule is symmetric, and a group is not kept
because its numbers are welcome.

**`20260829T210754Z-p4b`** — closing sample idle 79.53 %, busiest 36.8 %.

### A caveat disclosed rather than acted on

Groups 1, 2 and 3 each show xprotectd's lifetime-average CPU climbing across
the group — 2.30 -> 51.50, 4.70 -> 19.80, 3.10 -> 26.20 — which is XProtect
scanning the freshly built binary. None was discarded on that basis: the
closing-gate rule is written on idle and busiest process, all three pass it,
and discarding gate-passing groups until a number improves is the selection
bias the frozen regime exists to prevent. It is also the reason four groups
were taken with same-window reference rows rather than one group on its own.
Group 5, the window the restated criterion is read on alongside group 1,
shows xprotectd at 0.00 % at both ends and is free of the caveat entirely.
