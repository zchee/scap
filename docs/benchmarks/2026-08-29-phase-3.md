## W3.0b — the `.git` detection default

Deviation D-6 made this a Phase-3 obligation: the two strategies were never
compared directly, because W0.2 measured only open-and-scan and the shipped
jwalk walker only stat-first, and the corpora disagree about how much I/O each
costs. The rule was to measure both at `N*` = 4 on a′ and a+b and freeze the
default from those numbers.

### The matrix (run `20260829T124726Z-p3-w30b`, binary `250b292e`)

| Corpus | | open-and-scan | stat-first |
| --- | --- | --- | --- |
| a′ | median wall | 19.048 ms | **12.072 ms** |
| | user / sys | 6.411 / 44.994 | 4.204 / 22.264 |
| a | median wall | 117.031 ms | **115.035 ms** |
| | user / sys | 31.755 / 407.942 | 32.544 / 398.727 |
| a+b | median wall | 146.618 ms | **141.900 ms** |
| | user / sys | 39.416 / 507.988 | 39.523 / 492.542 |

**Stat-first wins every corpus.** The plan's expectation — that opening a
candidate pays for itself on a directory-dense tree, where most directories
have to be opened anyway — does not survive the measurement: a+b holds 21,360
directories against 1,822 repositories, the shape open-and-scan was predicted
to win, and it loses there too. An `openat` that returns a descriptor costs
more than a `statat` that returns `ENOENT` by more than the saved probe is
worth, at both corpus shapes this machine can offer.

### Decision

> **W3.0b frozen: default = stat-first.** Open-and-scan survives as
> `SCAP_LIST_DETECT=open`, an ADR-13 override, because the measurement is one
> filesystem and one corpus shape — around twelve directories per repository —
> and a tree far sparser in repositories is where it could still win.

Applied in `0b352d2` `perf(walk): freeze the default .git detection strategy`,
which also adds the README and CHANGELOG rows and a test naming the frozen
answer, so re-deciding it requires re-measuring rather than editing one
attribute.

## Where the user CPU goes

AC-3a's bound is 39.42 ms and the gate row spends 37.409, so it is worth
saying precisely what the 37 ms is. The `SCAP_LOG=debug` postprocess span on
a+b reads filter 3 µs, sort 86 µs, format 78 µs — **0.17 ms in total, and
invariant across 1, 4 and 8 threads** (five samples each). Fixed startup, read
from the `version` row's user CPU, is 1.135 ms. Everything else is the walk.

Splitting the walk by thread count, on the informational default-strategy
sweep below:

| `N` | total user | walk-attributable | extra user CPU vs `N` = 1 |
| --- | --- | --- | --- |
| 1 | 26.615 | 25.480 | — |
| 4 | 37.957 | 36.822 | **+11.341** |
| 8 | 51.180 | 50.045 | +24.565 |

**The walk spends 11.3 ms more user CPU at four threads than at one — 30 % of
the measured user time and 29 % of the AC-3a budget.** Post-processing is 0.4 %
of it and startup 3 %. The measured curve is user 26.6 → 38.0 → 51.2 and system
329 → 479 → 851 ms as `N` goes 1 → 4 → 8.

**Where that 11.3 ms goes is not established here, and the two causes this
section originally named are now refuted.** It attributed the figure to
`find_job` sweeping steal victims from index 0 and to `SPINS_BEFORE_PARK` = 32
not decaying. W3.5b rewrote both and measured no change, then counted what the
pool actually executes: at four threads the whole idle/steal path runs about a
thousand times across 36,471 directories, over roughly 70 idle episodes. The
per-episode arithmetic was right — a full `find_job` sweep really is one
`Injector` probe plus `n − 1` `Stealer` probes, so 32 non-decaying spins could
reach 128 shared-memory probes in one episode — but the episode count was the
missing factor, and 70 episodes cannot carry 11 ms.

See `docs/benchmarks/2026-08-29-w35b.md` for the execution counts, the four
variants measured against this tree, and the ±1 ms resolution limit that any
future attempt has to clear. The quantity above stands; the explanation does
not, and profiling it (W3.5c) precedes any further attempt to remove it.

## Host drift, and why the absolute bounds bite harder today

The frozen references were taken on 2026-08-28 and the machine has not held
still. The preserved pre-Phase-3 binary `0b48c24a`, re-measured in this
window, reads **144.877 ms** on a+b against the **135.358 ms** it read in its
own 10:00Z window, and **12.896 ms** on a′ against its own frozen **12.245**.
The same program, the same corpus, ~7 % slower. Every absolute bound in §9 is
therefore roughly 7 % tighter today than when it was frozen, which is most of
why the a+b legs read as close as they do and all of why the a′ leg is carried
by D-6's overlap arm rather than its absolute arm. This is the failure mode
D-6 was written to prevent: an absolute wall bound on a fixed-cost-dominated
corpus polices the machine, not the walker.

## An operational hole found in the watchdog

The chain runner tells its own `hyperfine` from a foreign one by looking for
`$REPO/docs/benchmarks/runs/` in the command line. That works against a
different project's sweep and **fails against a second lane in this
repository**, whose exports land under the same path and are therefore
classified as ours. It did not bite here — the Phase-0b lane's `rm` benchmark
started at 13:37:36Z, after the last group of this window finished — but it
would have gone undetected if it had not. A lane-specific marker in the run
directory name is already there and is what the check should match on.

## Counter semantics: `dirs_read` now follows the default

`dirs_read` counts directories whose entries were read, so it counts
repository directories only under open-and-scan. With stat-first frozen as the
default it reads **1,198** on a′ — reproducing the jwalk walker's count
exactly, which is continuity evidence across three walkers — and 2,042 under
`SCAP_LIST_DETECT=open`. Both are under AC-9's 2,100 bound. The figure
compares within a strategy, never across strategies or across versions, and
the CHANGELOG line that declared it changed at Phase 3 is corrected to say so.

cover repository-input parsing and the in-process configuration load — neither
touches the walker this phase rewrote — and the whole-program `scap root` /
`scap list` walltime targets that would cover it cannot run on this host:
`Failed to install exec-harness version 1.3.0 … there isn't a download for
your platform` on `aarch64-apple-darwin`, observed twice in the Phase-2b
window and deterministic. That layer is CI-only by design. Running
`cargo codspeed build` here would also have overwritten the measured
`target/release/scap`, the hazard the Phase-2b document records; the binary
this document names is the one every row above was taken on.
