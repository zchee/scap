# 2026-08-28 baseline — quiet-machine harness

Phase-0 measurements for
`docs/plans/2026-08-28-theoretical-limit-optimization.md`: the W0.1 baseline,
the W0.2 walker matrix, and the verdicts those two owe the W0.6 threshold
freeze. Every number here was produced by `scripts/bench-quiet.sh` and the
drivers under `.omc/bench/`, one benchmark at a time on a machine gated for
contention; the raw hyperfine JSON for every row is under
`docs/benchmarks/runs/`. Analysis is `scripts/bench-analyze.py`, which computes
the thread rule, the adoption rules and the gates on top of
`scripts/bench-compare.py`'s statistics.

Read the Deviations section first: the quiet gate does not measure what the
plan specified, for reasons recorded there.

## Deviations from the plan

### D-1 — the quiet gate measures CPU contention, not the load average

**What changed.** The plan (§6 W0.1, §0) specifies that the harness refuses to
run unless the 1-minute load average is below 2.0. `scripts/bench-quiet.sh`
instead requires **CPU idle ≥ 85 % and no single process above 15 % CPU**, each
taken as the median of three samples five seconds apart. The other two
preconditions are unchanged (`xprotectd` CPU < 5 %, no `cargo`/`rustc`
running), `SCAP_BENCH_FORCE=1` remains reserved for the loaded rows, and the
loaded rows keep their original definition (1-minute load ≥ 8, generated
synthetically). The load average is still sampled and **recorded** — in
`metadata.json` per run and in the tables below — it is simply no longer the
gate. Approved by the team lead on 2026-08-28; the user is to be informed, and
every row's raw hyperfine JSON is kept so any row can be re-run under whichever
gate the user prefers.

**Why.** The plan's threshold encodes the intent "no CPU contention". On this
Darwin host the 1-minute load average is decoupled from contention, so the
threshold does not express that intent. Measured over roughly forty minutes on
an otherwise idle desktop, the machine sat at 89.85 % idle (5.16 % user, 4.97 %
system) with four threads in the runnable state while the 1-minute load average
read 5.06, and the load average did not follow Chrome's CPU falling from 55 %
to under 9 %. Twelve consecutive samples:

| Time (UTC) | 1-min load average | CPU idle | Runnable threads |
| --- | --- | --- | --- |
| 10:54:34 | 3.67 | 81.55 % | 7 |
| 10:54:47 | 3.65 | 88.30 % | 3 |
| 10:55:00 | 4.64 | 91.15 % | 3 |
| 10:55:12 | 4.88 | 84.53 % | 3 |
| 10:55:25 | 4.90 | 87.15 % | 2 |
| 10:55:38 | 4.56 | 93.15 % | 4 |
| 10:55:50 | 4.16 | 93.50 % | 2 |
| 10:56:03 | 15.15 | 66.39 % | 7 |
| 10:56:16 | 13.36 | 86.31 % | 3 |
| 10:56:28 | 10.54 | 78.59 % | 3 |
| 10:56:41 | 8.92 | 92.17 % | 2 |
| 10:56:54 | 7.46 | 89.93 % | 4 |

The load average never approaches 2.0, and at the highest idle reading
(93.50 %) it still reads 4.16. Under the original gate no row would ever have
been measured on this machine.

The measurement run itself produced the sharpest illustration. At 11:23:55Z the
gate admitted the machine at **90.97 % idle with a 1-minute load average of
13.93**, moments after a burst had driven idle down to 2.83 % and the run had
correctly discarded the group in flight. Because the load average is a
one-minute exponentially-weighted mean it stays elevated long after the
contention that caused it has gone, so it both refuses an idle machine and
keeps refusing it for a minute after any disturbance ends. The idle figure
tracks the actual state at the moment the row runs, which is what a benchmark
gate needs.

**What the original gate would have done.** It would have refused every run
above, including the seven samples at 87–93 % idle where the machine was
genuinely free. Conversely it would have *passed* nothing that the new gate
rejects unfairly: on the condition §0 actually describes — load average 18.9
with `xprotectd` scanning fresh binaries and two concurrent `hyperfine`
sessions — the idle test fails outright, so the new gate is strictly stronger
where it matters. It demonstrated this during setup: a `cargo install` of
rustup pushed three `rustc` processes to ~95 % CPU and `xprotectd` to 96 %, and
the gate refused with `idle=51.66% top_proc=100.0% xprotectd=87.00% cargo
rustc`. A forced run under that load read the empty binary at 2.9 ms against
1.91 ms on an idle machine — a 52 % inflation, which is exactly the
contamination the gate exists to prevent.

**Section ordering.** Because idle time is the scarce resource, sections run
most-latency-sensitive first: the AC-6 rows (empty binary, `scap --version`),
then the AC-1 `scap root` rows, then the baseline lists, the W0.2 matrix, W0.5,
W0.3, and the loaded rows last.

### D-1a — `kernel_task` and `WindowServer` are excluded from the busiest-process clause

The busiest-process clause keeps its 15 % bound, but `kernel_task` and
`WindowServer` are excluded from the scan alongside the probe's own `top` and
`ps`. Without the exclusion the clause is unsatisfiable here for the same
reason the load average was: on a fully idle machine those two sit at 19–23 %
and 14–22 % respectively, so the clause fires on the machine's own floor rather
than on contention. Both are unavoidable macOS infrastructure on a host with a
display — `kernel_task` on Apple Silicon is largely thermal and power
management, and is in part an accounting artifact rather than a competing
workload — and both are already counted in the idle figure, so excluding them
hides no contention. What the clause still catches is its real target: a user
process pegging a core while the idle figure stays high, which the idle test
alone would miss on a 16-core box. Observed on an idle machine after the
exclusion, the busiest remaining process was a Claude helper at 10–16 %, which
the median of three samples holds under the bound.

### D-2 — W3.0 is evaluated on the raw-reader family's best member; the B2 adoption rule then picks the reader

**What changed.** The W3.0 gate ("does a new walker beat jwalk?") and Decision
B's adoption rule ("which reader ships, B1 or B2?") interact: on corpus a′,
`b1-deque` passes the W3.0 gate against `D_wall` and `b2-rustix` does not, by
0.13 ms of confidence-interval overlap. The lead's ruling composes the two
rules rather than letting evaluation order decide the outcome by accident: the
W3.0 gate answers "new walker vs. jwalk" and is evaluated on the best member of
the raw-reader family on the shared scheduler — `b1-deque` — and, once that
question is settled, the B2 adoption rule (`CPU(B2) <= 1.05 x CPU(B1)` at
`N*`) picks the reader that ships. `b2-rustix` ships.

| Corpus | `D_wall` (`b3-jwalk` at its own `N*`=4) | `b1-deque`@4 | `b2-rustix`@4 |
| --- | --- | --- | --- |
| a′ | 20.32 ms (IQR 19.70-22.18) | 18.91 ms, 95% CI of median diff [-2.46, -0.56] → **PASS** | 19.66 ms, CI [-1.66, +0.13] → **FAIL** if evaluated alone (0.13 ms overlap) |
| a+b | 172.54 ms (IQR 166.25-180.47) | 119.87 ms, CI [-59.05, -47.88] → **PASS** | 121.79 ms (IQR 121.08-123.53), CI [-57.16, -45.95] → **PASS** |

(The a+b CIs are the same figures already in the "W3.0 gate inputs" table
below; nothing here is recomputed from raw JSON.)

**a′ is a weak discriminator by construction.** a′ holds 2,036 directories,
24,313 entries and 841 repositories; at roughly 20 ms wall the run is
dominated by fixed cost — process spawn, config resolution, output — rather
than by traversal, so a 0.13 ms confidence-interval overlap sits inside the
fixed-cost noise floor, not inside a real difference between the readers. The
W3.0 gate was designed to discriminate traversal engines, which a′ cannot do
at this size; a+b, at 21,360 directories, is the corpus that actually
discriminates. The a′ leg is still recorded above rather than discarded, and
this composed rule is itself a numbered deviation so the W0.6 freeze can cite
it.

### Instrument bugs found and fixed while validating the harness

Both were in the measurement tooling itself, not in scap, and both were caught
by rehearsing the drivers against the real binaries rather than trusting them.
They are recorded here because each would have silently corrupted or destroyed
a run.

1. **The busiest-process figure came from `ps -o %cpu`, which is a lifetime
   average.** `ps` reports each process's mean CPU over its entire lifetime,
   not its current activity, so a browser idle for an hour still reads busy
   while a build started ten seconds ago reads idle — the opposite of what the
   gate needs. Compounding it, the probe's own `top` process was itself
   selected as the busiest at 73.8 %. Both figures now come from a **single
   `top -l 2` interval sample**: the first `top` sample reports usage since
   boot and only the second is an interval measurement, so the live table is
   everything after the last `%CPU` header, and the idle percentage and the
   busiest process are read from that one sample. Taking both from the same
   sample also keeps them mutually consistent.
2. **The section drivers passed hyperfine `-- <binary> <args>`.** In hyperfine
   every positional argument after `--` is a *separate benchmark*, not one
   command's argv, so the runner was launching the spike binary with no
   arguments — which exits 2 on its usage message — and treating each flag as
   another benchmark. The row failed in its first warmup run. Every driver now
   passes one command string per benchmark and lets hyperfine split it under
   `-N`, which is the form `.omc/spikes/w02-walker/RUN.md` and its `matrix.sh`
   print.

## Protocol

- **Quiet-machine gate** (`scripts/bench-quiet.sh`, as amended by D-1/D-1a):
  refuses to run unless CPU idle is >= 85 % and the busiest process (excluding
  `kernel_task`, `WindowServer`, and the probe's own `top`/`ps`) is <= 15 %,
  both the median of three samples five seconds apart, and `xprotectd` CPU is
  < 5 % with no `cargo` or `rustc` running. A violated precondition names the
  failing check and exits 3. The 1-minute load average is recorded, not gated.
  `SCAP_BENCH_FORCE=1` overrides the gate and is reserved for the
  loaded-machine rows.
- **One benchmark at a time** (plan §0 measurement lesson): the first §0 batch
  ran two hyperfine sessions concurrently and re-ran under load average 18.9,
  inflating wall times up to ~2x. Every row here is one `hyperfine` invocation,
  run sequentially, never two at once.
- **Per-row abort.** Each driver re-checks contention between rows and aborts
  the section rather than record a row taken under load; sections are resumable,
  so a retry re-runs only the rows that have no JSON. Every abort and retry in
  this run is in `.omc/bench/run-all.log`.
- Each row is `hyperfine -N --warmup 5 --runs 30 --export-json`. Wall figures
  are medians over 30 runs with the interquartile range; hyperfine reports only
  mean `user`/`system`, so every CPU figure is a mean. All values in ms.

## Verdicts

### Thread selection — `N*` = 4 for every variant

The rule (plan §2, Decision B), verbatim: on corpus a+b, `N* = smallest
N in {1, 2, 4, 8, 12, 16}` such that `median wall(N) <= 1.10 x min_N median
wall(N)` **subject to `sys(N) <= 1.5 x sys(1)`**. Applied to each variant it
selects **4 threads in every case** — across three schedulers, two raw readers,
`getattrlistbulk`, and jwalk alike. Wall time does not merely plateau past four
threads, it regresses: `b1-deque` on a+b runs 346 ms at 1 thread, 198 at 2, 120
at 4, then back up to 131 at 8, 201 at 12 and 223 at 16. §0's expectation that
16 threads would be fastest came from a loaded window and does not survive a
quiet one.

### H1 and H2 are both refuted; sys inflation is not a scheduling property

All three B1 schedulers share one reader and one corpus, so any difference
between them is scheduling and nothing else. System time as a multiple of each
arm's own single-thread figure, on a+b:

| Threads | shared LIFO | shared FIFO | per-thread deque |
| --- | --- | --- | --- |
| 1 | 1.00 | 1.00 | 1.00 |
| 2 | 1.14 | 1.16 | 1.14 |
| 4 | 1.35 | 1.40 | 1.32 |
| 8 | 2.91 | 3.05 | 2.82 |
| 12 | 6.35 | 6.59 | 6.62 |
| 16 | 9.11 | 8.53 | 8.72 |

The three arms are indistinguishable. **H1** predicted the per-thread deque
with oldest-end stealing would hold inflation at or below 1.1x at four threads;
it is 1.32x. **H2** predicted the shared LIFO caused §0's 1.96-2.45x inflation;
the deque, which is not a shared LIFO, inflates 2.82x at eight threads against
the LIFO's 2.91x. The inflation is inherent to concurrent `readdir` on this
filesystem, not a consequence of how work is scheduled.

This contradicts plan §0 conclusion 2 ("sys inflation is a **scheduling**
property (H1/H2), not an inherent cost of threads"). That conclusion rests on
comparing jwalk's system time at four threads (601 ms) against the *prototype's*
single-thread system time (571 ms) — two different programs, not the same
program at two thread counts. Because the comparison mixes programs, §0
conclusion 2 must be corrected in the W0.6 freeze commit; the controlled
version of that test is the table above.

jwalk does behave differently, but not because of its scheduler. Its system
time at four threads is 0.95x its own single-thread figure, genuinely flat, and
that is because its single-thread system time is already 673-708 ms against the
raw readers' 327 ms: the per-directory `stat` calls this plan removes give it
more than twice the kernel work per directory, so it saturates later. Put
another way, the inflation ratio differs because the syscall baseline differs —
jwalk starts at 708 ms sys single-thread vs 326 ms for the raw readers — not
because of scheduling. In absolute terms it is worse at every thread count.

### B2 is adopted — the shipped walker needs no `unsafe`

The rule: adopt B2 instead of B1 iff `CPU(B2) <= 1.05 x CPU(B1)` on a+b. At
each variant's `N*` of 4, `b2-rustix` costs **464.9 ms** of CPU against
`b1-deque`'s **457.9 ms**, a ratio of **1.015**. The plan predicted rustix's
owned `CString` per entry would cost 4-8 ms; measured across 204,800 entries it
is about 7 ms of user CPU (34.0 ms against 26.3 ms).

Consequence: the safe `rustix::fs::Dir` API is what ships. ADR-11's unsafe leaf
in `src/walk/sys.rs` is not needed, the crate-root `deny(unsafe_code)` needs no
module-level `allow` site, and R5 reduces to "there is no unsafe".

### W3.0 gate — passes on a+b for both readers, and on a' only for B1

`D_wall` is `b3-jwalk` at its own `N*`, which the thread rule also puts at 4 —
the same `RayonNewPool(4)` that W2b.1 ships.

| Corpus | `D_wall` | `b1-deque` | `b2-rustix` |
| --- | --- | --- | --- |
| a' | 20.32 ms (IQR 19.70-22.18) | 18.91 ms (IQR 18.47-19.87), CI [-2.46, -0.56] excludes 0 → **PASS** | 19.66 ms (IQR 19.16-20.53), CI [-1.66, +0.13] includes 0 → **FAIL** |
| a+b | 172.54 ms (IQR 166.25-180.47) | 119.87 ms (IQR 119.16-121.03), CI [-59.05, -47.88] → **PASS** | 121.79 ms (IQR 121.08-123.53), CI [-57.16, -45.95] → **PASS** |

The system budget holds for both: 431 ms at `N*` against the 490.45 ms
ceiling of `1.5 x sys(1)`. User CPU falls 5.2x, from jwalk's 178.5 ms to
34.0 ms.

**Unresolved rule interaction, for W0.6.** Decision B's adoption rule selects
B2 on CPU parity; the W3.0 gate requires the winning variant to beat `D_wall`
on a' **and** a+b, and B2 fails the a' leg while B1 passes it. Read in
sequence the two rules send Phase 3 to the B3 fallback — no new walker at all —
despite a 1.44x wall win and a 5.2x user-CPU win on a+b. Worth weighing: the a'
margins are 1.4 ms out of 20 ms. Corpus a' holds only 2,036 directories, so it
is dominated by fixed costs (process start, 841 repository checks, output), and
the per-directory `stat` overhead the raw readers remove is only 2,036 stats
there. That is why jwalk is nearly competitive on a' and loses badly on a+b's
21,360 directories. B2 fails by 0.13 ms of confidence-interval overlap. This
document records the measurement; the resolution is a plan judgement for W0.6.

### B4 rejected — the OBJTYPE hypothesis is confirmed

Compared only against `b1-deque`, the one variant sharing its scheduler
(RUN.md §8), `b4-attrbulk` at `N*` = 4 on a+b shows **lower** user CPU
(22.7 ms against 26.3 ms, 0.86x) but **2.16x** the system time (930.6 ms
against 431.6 ms) and roughly double the wall (243.7 ms against 119.9 ms). The
CORRECTNESS.md §6 hypothesis — that asking `getattrlistbulk` for
`ATTR_CMN_OBJTYPE` forces vnode resolution and costs kernel time — is
**confirmed**.

### Counter agreement — every timing row is valid

All six variants report byte-identical `dirs_read`, `entries`, `repos`,
`fstatat` and `excluded` on each corpus, matching the frozen values: a =
17,771 / 153,406 / 841; b = 3,589 / 51,394 / 981; a+b = 21,360 / 204,800 /
1,822; a' = 2,036 / 24,313 / 841 (with `excluded=1`). No variant drifted, so no
timing row is void (RUN.md §3).

### AC-6 fails on the baseline itself

`scap --version` has a median of **2.57 ms** against the empty binary's
**2.18 ms**, a delta of **0.391 ms** against AC-6's 0.3 ms bound. The 95 %
bootstrap interval for the difference of medians is **[0.195, 0.518] ms**, so
the cost is real and excludes zero, but the 0.3 ms bound lies inside the
interval — the criterion is written at roughly the resolution limit of the
measurement. The interquartile boxes are not disjoint; they touch at 2.458
against 2.439. The cost is user CPU (+0.240 ms) rather than system (+0.016 ms),
matching §0's attribution to the clap build and `tracing_subscriber` init at
src/lib.rs:15-22 — which is what W1.4 exists to reduce. Since AC-6 gates every
Phase-1 commit, a threshold the tree already violates would block W1.1, W1.2 and
W1.4 on arrival. Recorded for W0.6 to resolve.
