The output-equality clause is satisfied trivially and that is worth stating
plainly rather than hiding behind a PASS: the excluded subtree contains **no
repository at all**. It is 15,735 directories of `node_modules.bak` under
`github.com/zchee/claude-code.bak`. So the set of "lines prefixed
`github.com/zchee/claude-code.bak/`" is empty, the required diff is the empty
diff, and the exclusion removes 93 % of the walk's directory reads while
changing nothing a user sees. That is the whole point of Decision B7.

`scap list` on corpus a: **16,933** directory reads without the exclusion,
**1,198** with it.

## AC-8b — rule (v) against the ghq oracle

`chmod 000` directory under a root holding two readable repositories, ghq
1.8.0 as the oracle, default settings (no log variable — the WARN subscriber
W1.4 always builds):

| | stdout | exit | stderr |
| --- | --- | --- | --- |
| ghq | `github.com/a/x`, `github.com/b/y` | 0 | `warning <path>: Permission denied` |
| scap | `github.com/a/x`, `github.com/b/y` | 0 | `WARN scap::cmd::list: <path>: Permission denied` |

Byte-identical stdout, same exit status, and the same message text after the
tool's own decoration. **PASS.** Pinned by
`tests/parity_ghq.rs::unreadable_directory_is_skipped_like_ghq`, which is not
`#[ignore]`d and skips only when no oracle is configured.

Stderr is reserved for that case. Rule (v)'s "generic warn with the io error
for others" is emitted at **debug** level instead, because ghq prints nothing
for those and `follow_links(true)` makes them ordinary: corpus a holds one
stale documentation symlink, and warning on it would put a line on every
`scap list` the maintainer runs, which teaches users to stop reading stderr
and so costs more than it reports. Verified on the real corpus — default
settings produce **0 bytes** of stderr, `SCAP_LOG=debug` names the link.
W2b.2's `follow_links(false)` removes the class from the walk entirely. The
rule (vi) root cases still warn: a root scap cannot walk hides every
repository beneath it, not one entry.

## Counter semantics: why 1,198 and not the frozen 2,036

`dirs_read` counts directories whose entries were read. The W0.2 spike and
the shipped jwalk walker legitimately disagree on that number for the same
corpus, because they find `.git` differently: the spike reads a repository's
directory and looks for `.git` in the entry buffer, while the jwalk walker
detects it with a `stat` and therefore **never opens a repository
directory**. The spike thus counts one extra read per repository it opens.

The derivation below is self-contained; the counts were obtained from the
W0.5 path dumps, which are **local, untracked artifacts** and are
deliberately not committed because every line is an absolute path under the
maintainer's home directory (the same reason Phase 0 kept them out of the
tree). They live at `docs/benchmarks/runs/20260828T104448Z-w05/a.dump` and
`aprime.dump`, and are regenerable with `spikewalk --dump-dirs` per
`.omc/spikes/w02-walker/RUN.md` §"Capture the path set":

```
spikewalk --variant b1-deque --threads 8 --dump-dirs results/a.dump \
    /Users/zchee/src 1>/dev/null
spikewalk --variant b1-deque --threads 8 --dump-dirs results/aprime.dump \
    --exclude github.com/zchee/claude-code.bak /Users/zchee/src 1>/dev/null
```

Each dump holds one `D <abs path>` line per directory read and one
`R <abs path>` line per repository found: 17,771 D and 841 R for corpus a,
2,036 D and 841 R for corpus a′, matching the ledger #2 counters exactly.

**The 840.** Intersecting the spike's 841 repository paths with its own
directory list gives **840** — every repository it found, it also opened,
with one exception. The exception is `github.com/kouzoh/platform-proto`, a
symlink to a repository under `~/go/src`: ADR-9 rule (iii), emitted at the
link path and never descended. The same 840 holds on the a′ dump.

| | frozen 2026-08-28 | = non-repo dirs | + repos opened |
| --- | --- | --- | --- |
| corpus a | 17,771 | 16,931 | 840 |
| corpus a′ | 2,036 | 1,196 | 840 |

So on the frozen corpus this walker would read **1,196**; it reads **1,198**
today. Phase 3's reader-based walker will count 2,036 again on the frozen
corpus, because it opens repository directories the way the spike does.

So **+4 repositories and +2 non-repository directories**, and that +2 is
exactly the gap between the 1,196 the reconciliation predicts and the 1,198
measured — confirmed independently on corpus a (16,931 → 16,933) and on
corpus a′ (1,196 → 1,198). Against corpus a's 16,933 reads the drift is
≈ 0.01 %.

Corpus b's zero drift corroborates that only corpus a changed. It fits the
same reconciliation: 3,589 − 2,613 = 976 repositories opened out of 981, so
five not opened — the same symlink-and-bare-repository pattern.

**The AC-3 references for a+b remain the frozen W0.1 numbers on the
2026-08-28 corpus** (median wall 156.15 ms, user CPU 171.38 ms, `list_ab`).
This drift does not reopen them; it is recorded so that a later run can tell
whether it walked the same tree.

`scripts/bench-quiet.sh` now records this inventory in every run's
`metadata.json` under `corpus_inventory` — measured `repos`, `dirs_read` and
`excluded` per corpus the selected rows walk, the frozen reference, and
`repos_drift`. One `scap list` per corpus runs before the timed rows, so it
never lands between two hyperfine invocations. A binary older than W2b.1
emits no `scap::walk::root` span and records both counters as `null` rather
than failing the run.

## Deferred (competing benchmark on the host)

Four items have **no measurement** and are not evaluated here. They move to
the Phase-2b gate lane.

1. **AC-9's wall clause** — `list_aprime` median wall against the 49.34 ms
   bound, via `docs/benchmarks/extra-rows-w2b1.sh`.
2. **The second freeze point** — the a′ reference triple ⟨W2b.1 median wall
   (a′)⟩, ⟨W2b.1 user CPU (a′)⟩, ⟨W2b.1 CPU (a′)⟩ that §9 AC-3a / AC-3d /
   AC-3′ carry as **OPEN** (plan §6, W0.1 "a′ reference (edit 1)").
3. **The three deferred Phase-2 groups** — `p2-list` (AC-1's `scap list`
   CPU-difference row), `p2-ac6` (AC-6 on the Phase-2 binary), and
   `p1-w14-inplace`. This is their **fourth** refusal.
4. **The optional 60-run tightening** of `root_pinned_root_cwd`.

Reason, recorded because it is a different one from the previous three
refusals: a **second benchmark suite held the host** — the bfs-cpp
`baseline-matrix` driver under
`/Users/zchee/src/github.com/zchee/bfs-cpp/bench/`, writing into
`bench/results/2026-08-29/raw/` throughout every attempt.

Two consequences, either disqualifying on its own. The D-1a contention gate
refused every attempt outright, idle oscillating around 83 % against the
85 % floor. And even had it opened, a row taken beside another hyperfine
session is exactly the §0 measurement error this harness exists to prevent —
"the first batch ran two hyperfine sessions concurrently" — so the number
would not have been usable.

The shape of that suite is why no amount of waiting helped. It **respawns
one hyperfine per row**, roughly every 70–80 s, across a matrix of corpora —
one of which is `/Users/zchee/rust/src`, the volume this repository sits on,
so it competed for the same filesystem these rows measure and not merely for
CPU. Between two rows there is a genuine gap with no hyperfine alive. A
45-minute bounded wait sampling every 30 s caught **six** such gaps
(08:19, 08:22, 08:27, 08:35, 08:38, 08:47 UTC) and correctly refused every
one: the rule requires two consecutive clear samples, and starting inside a
gap would have collided with the next row within seconds. Killing a single
hyperfine would not have helped either — the pid changed on every
observation (15873, 36434, 33311) because the driver spawns a fresh one per
row; only stopping the driver script would open a window.

**The gate was never forced and no partial run directory was kept.** Lead
ruling 2026-08-29: defer, commit the wave, take these rows later.

The binary they must be measured against is preserved at
`scratchpad/p2b/scap-w2b1-inplace`, sha256
`0b48c24a65ce86f14fa9b0301617a12442773bfb4ed3efeba4eba6b6ef344155`, so the
a′ freeze point can be taken against this exact artifact rather than a
rebuild.

Note that the competing suite and the corpus drift have one cause:
`bfs-cpp` is one of the four repositories added to corpus a.
