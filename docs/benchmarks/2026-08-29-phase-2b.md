## Counter semantics: why 1,198 and not the frozen 2,036

`dirs_read` counts directories whose entries were read. The W0.2 spike and
the shipped jwalk walker legitimately disagree on that number for the same
corpus, because they find `.git` differently: the spike reads a repository's
directory and looks for `.git` in the entry buffer, while the jwalk walker
detects it with a `stat` and therefore **never opens a repository
directory**. The spike thus counts one extra read per repository it opens.

The derivation below is self-contained; the counts were obtained from the
W0.5 path dumps, which are **local, untracked artifacts** and are
deliberately not committed because every line is an absolute path under the
maintainer's home directory (the same reason Phase 0 kept them out of the
tree). They live at `docs/benchmarks/runs/20260828T104448Z-w05/a.dump` and
`aprime.dump`, and are regenerable with `spikewalk --dump-dirs` per
`.omc/spikes/w02-walker/RUN.md` §"Capture the path set":

```
spikewalk --variant b1-deque --threads 8 --dump-dirs results/a.dump \
    /Users/zchee/src 1>/dev/null
spikewalk --variant b1-deque --threads 8 --dump-dirs results/aprime.dump \
    --exclude github.com/zchee/claude-code.bak /Users/zchee/src 1>/dev/null
```

Each dump holds one `D <abs path>` line per directory read and one
`R <abs path>` line per repository found: 17,771 D and 841 R for corpus a,
2,036 D and 841 R for corpus a′, matching the ledger #2 counters exactly.

**The 840.** Intersecting the spike's 841 repository paths with its own
directory list gives **840** — every repository it found, it also opened,
with one exception. The exception is `github.com/kouzoh/platform-proto`, a
symlink to a repository under `~/go/src`: ADR-9 rule (iii), emitted at the
link path and never descended. The same 840 holds on the a′ dump.

| | frozen 2026-08-28 | = non-repo dirs | + repos opened |
| --- | --- | --- | --- |
| corpus a | 17,771 | 16,931 | 840 |
| corpus a′ | 2,036 | 1,196 | 840 |

So on the frozen corpus this walker would read **1,196**; it reads **1,198**
today. Phase 3's reader-based walker will count 2,036 again on the frozen
corpus, because it opens repository directories the way the spike does.

## CodSpeed

Informational, and **not comparable with anything else in this directory**:
the `docs/benchmarks/` rows are taken on a quiet machine under the plan's
frozen D-4 `RUSTFLAGS`, while CodSpeed builds with clean flags.

The divan suites ran under the walltime instrument and uploaded:
**<https://app.codspeed.io/zchee/scap/runs/6a92b24252831271b7d73c61>**
(`cargo codspeed build -m walltime`, then `codspeed run -m walltime --
cargo codspeed run`; 26 benchmarks across the `url` and `config` suites).
`zchee/scap` is enabled on codspeed.io and the local CLI is authenticated, so
this is a real `local` run rather than a dry run.

Read the numbers with care. Walltime is designed for dedicated hardware, and
on a developer laptop its dispersion is large — `rule_a_scap_root_env`
reports σ = 1219 % around a 124 ns best time, and `load_absent` σ = 150 %.
The stable rows agree with the plain-divan figures recorded in ledger #28b
(`rule_c_plain_last` 60 ns here against 55.71 ns there; `rule_c_eight_plain_roots`
34 ns against 35.2 ns), which is the useful signal: the shape is reproducible
even where the walltime dispersion is not.

**The `codspeed.yaml` exec targets cannot run on this platform.**
`codspeed run -m walltime` with no command fails at
`Failed to install exec-harness version 1.3.0 … there isn't a download for
your platform aarch64-apple-darwin`. The exec layer is therefore CI-only,
which is consistent with how it was designed — the workflow already pins it
to `runs-on: codspeed-macro` behind `vars.CODSPEED_WALLTIME`. The three
targets were verified to run correctly by hand against the generated fixture
(`scap root` prints the fixture root; `scap list` prints 1,800 lines;
`scap list --unique repo-007` prints 120), and timed informally with
hyperfine on the same machine state for a cross-check against the harness's
`list` rows: `scap root` 5.1 ms ± 0.2, `scap list` 8.9 ms ± 0.7, `scap list
--unique repo-007` 8.6 ms ± 0.4 over 30 runs. Those are not gate rows, are
not committed as a run directory, and measure a different corpus (1,800
synthetic repositories in a shallow tree) from corpus a's 845 in a deep one —
the fixture walk is roughly an order of magnitude cheaper than corpus a's
115.8 ms, which is what a tree with no `node_modules`-shaped subtrees should
cost.

**Caution for anyone running the CodSpeed lane locally:**
`cargo codspeed build` writes its instrumented binary to
`target/release/scap`, overwriting the release binary the hyperfine harness
measures. It was overwritten here (2,396,440 B, sha256 `69a7bd3a…`) and
restored with a plain `cargo build --release` back to `bc5bc21c…`. No
measurement in this document was affected — every run directory records the
`binary_sha256` it actually measured, and all seven groups plus the V-4 and
output-equality checks ran before the CodSpeed lane started. This is the same
hazard that cost ledger #16 its first V-4 hash; re-fingerprint the binary
after any CodSpeed build.
