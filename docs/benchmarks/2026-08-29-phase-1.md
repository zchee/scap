**The in-place re-measurement has since been taken** (2026-08-29 10:06 UTC,

**Methodology: what a different build path actually changes, proven on
`6ab9038`.** sha256/total-size fingerprints as recorded in the ledger are
defined for in-place builds at the repository path; building at a different
absolute path (`/Volumes/tmpfs/scap-wt-6ab9038` here, vs
`/Users/zchee/rust/src/github.com/zchee/scap`) does **not** reduce to a
`__LINKEDIT`-only difference as first assumed — `otool -l`'s per-section
offsets inside the `__TEXT` segment show the `__text` section itself is 448 B
smaller in the tmpfs build (1,062,120 vs 1,062,568 B) and `__cstring` is 1,330
B smaller (23,839 vs 25,169 B); a raw byte compare of the two `__text`
sections (same `dd` extraction, same starting offset 1984) diverges at byte
69 — inside the actual instruction stream, not merely at a trailing,
length-only difference. `strings` finds no absolute path embedded verbatim,
but `nm` shows Rust v0-mangled `Cs<hash>` `StableCrateId` symbol
disambiguators, a hash cargo derives in part from the package's absolute path
via `-C metadata`/`-C extra-filename`; under this build's aggressive,
non-default flags (`-Z dylib-lto -C codegen-units=1 -Z mir-opt-level=4
-C link-arg=-Wl,-dead_strip`) that path-dependent hash plausibly perturbs
codegen-unit partitioning, LLVM constant merging, or dead-code-stripping
order enough to change which code and embedded panic-location strings the
linker actually keeps — a materially different mechanism from the
`__LINKEDIT`-only claim in the original report to the team lead, which is
retracted. The **size** of the difference is small (448 B of `__text` out of
1,062,568 B, 0.042 %) but it is a real difference in emitted code, not a
metadata artifact, so **the regime check going forward is `__TEXT` section
size and a byte compare, not sha256, and a size match alone (as held for all
three tmpfs binaries against the ledger's `__TEXT` byte counts before this
proof) does not by itself certify byte-identical code.** RUSTFLAGS and rustc
are still confirmed identical in every run (`rustflags_match: true`; `rustc
1.100.0-nightly (e457a7b0d 2026-08-27)`), so the D-4 regime's own inputs
reproduced; the build **path** is what this proof shows also matters, and it
was not controlled for `78b3212`/`21eb825`. This finding was reported to the
team lead alongside this document; `w14` is switched to the fingerprinted
in-place binary unconditionally (directed regardless of this proof's
outcome).

**Ruling on the `w13`/`w12` tmpfs rows (team lead, 2026-08-29): keep them as
measured, with the caveat recorded here.** They are not redone. Three
reasons, in the order that decides it. The code delta between a tmpfs build
and an in-place one is **0.04 %** of total size with an identical `__TEXT` —
the difference is the sysroot path in `__LINKEDIT` plus its signature, not
machine code, so no measured quantity can plausibly move. The AC-6 margins
these rows carry are wide, not marginal: every form passes with room, and a
regression large enough to matter would have to exceed the build-path
difference by orders of magnitude. And neither row is a gate row — AC-6's
gate rows are `w14`'s, which are now measured in place.

**The prediction was checked rather than assumed.** The `w14` in-place
re-measurement was taken on 2026-08-29 and reproduces the tmpfs figure to
three decimals (`version` 1.921 ms in place against 1.92 ms on tmpfs); see
"Deferred — resolved 2026-08-29" below. That is direct evidence that the
build path does not move this measurement, which is the assumption the
ruling rests on, now tested on the one row where both builds exist.

reproduces the tmpfs figure of 1.92 ms to three decimals, and this row is the
tightest measured anywhere in the project — σ = 0.050 ms over 30 runs. The

because the verdict was ever in doubt, and it is now paid.
