# W3.5b — the pool's user CPU is not in the idle/steal path

Phase 3's gate measured the walk spending about 11 ms more user CPU at four
threads than at one, and `docs/benchmarks/2026-08-29-phase-3.md` attributed it
to two named values in `src/walk/pool.rs`: `find_job` sweeping steal victims
from index 0, and `SPINS_BEFORE_PARK` = 32 not decaying. W3.5b was chartered to
remove that overhead by rewriting the idle path.

**It did not, and the attribution was wrong.** Four variants were built and
measured; none moved the number by more than the harness can resolve. Counting
what the pool actually executes shows why: the idle/steal path runs about a
thousand times per walk, against 36,471 directories. No code change landed.

| | |
| --- | --- |
| CPU | Apple M3 Max — `hw.perflevel0` 12 Performance cores, `hw.perflevel1` 4 Efficiency cores, `hw.ncpu` 16, `hw.cachelinesize` 128 |
| OS | macOS 27.0, build `26A5421a` |
| rustc | 1.100.0-nightly (`e457a7b0d` 2026-08-27), ADR-12 pin `nightly-2026-08-28` |
| hyperfine | 1.20.0 |
| `RUSTFLAGS` | the D-4 frozen regime; `rustflags_match: true` in all five runs, `forced: false`, `allow_flags: false` |
| Corpora | a = `/Users/zchee/src`, b = `/Users/zchee/go/src`, a+b = both |
| Builds | in place in `target/release/`, per ledger #11b |

The core topology is recorded because it rules out a hypothesis rather than
because it explains one: with 12 Performance cores available, four worker
threads are not competing for a scarce core type, so Efficiency-core placement
cannot be what makes four threads cost more user CPU than one.

## The variants

All four apply cleanly to `d626460` and are preserved as patches in
`runs/20260829T145016Z-w35b-3way/`. **None of them landed.**

| | patch | change |
| --- | --- | --- |
| **d1** | `design1.patch` | The charter's design, idle/steal path only: victim order rotated to `(me + 1 + attempt) % n`; on an empty local deque one injector probe plus at most one victim per spin instead of a full sweep; `spin_loop` on `Steal::Retry` instead of a tight retry loop; spin budget 16, halving to 1 across consecutive parks; `notify_one` on ordinary pushes with `notify_all` kept for the terminal path |
| **d2** | `design2.patch` | **d1 plus** `in_flight` on a cache line of its own and one atomic read-modify-write per job instead of two — a `Retire::settle` that folds the child count and the retirement into a single `fetch_add` |
| **d3** | `design3.patch` | HEAD with `pool.rs` untouched, and `live_fds` moved onto a cache line of its own. It is declared next to `Ctx`, whose `detect`, `exclude` and `fd_cap` every worker reads for every directory entry, so its read-modify-writes plausibly invalidated a line the whole pool reads |
| **d4** | `design4.patch` | d1, d2 and d3 together |

**d2 is not an independent arm: it contains every d1 change.** So does d4. Only
d3 is disjoint from d1. This matters for reading the table below and is stated
here because an earlier draft of this analysis described d2 as built on HEAD.

## Execution counts — the finding that settles it

Atomic counters were compiled into a throwaway binary (`counters.patch`, d1
plus counters, never committed) and printed at the end of `pool::run` under
`SCAP_POOL_COUNTERS`. Corpus a+b is two roots, so each process makes two `run`
calls; the figures below sum both. Two invocations per thread count, ranges
shown where they differ.

| `N` | jobs | `steal_one` calls | victim probes | spins | parks | `wake()` calls | `in_flight` RMWs |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 36,471 | 17 | 0 | 0 | 0 | 11,039 | 47,510 |
| 2 | 36,471 | 210–263 | 196–249 | 148–180 | 15 | 11,039 | 47,510 |
| 4 | 36,471 | 1,023–1,258 | 1,009–1,244 | 771–982 | 68–79 | 11,039 | 47,510 |
| 8 | 36,471 | 3,350–3,352 | 3,336–3,338 | 2,592–2,611 | 247–266 | 11,039 | 47,510 |

**At four threads the entire idle/steal machinery executes about a thousand
times across a walk of 36,471 directories — three probes per hundred
directories, spread over roughly 70 idle episodes.** A few thousand atomic
probes cannot cost 11 ms.

The per-episode arithmetic in the Phase-3 doc was right: a full `find_job`
sweep is one injector probe plus `n − 1` stealer probes, so 32 non-decaying
spins really could reach 128 shared-memory probes in one idle episode at four
threads. The missing factor was the number of episodes. There are about 70,
not the thousands the 11 ms would require.

The counters binary is proof rather than assertion: rebuilding from
`counters.patch` reproduces sha256
`4299eee635013644f4eb15ce09afc10148cf02832b09d9e1662558a5a6c56562`
byte-for-byte, which is the binary the counts were read from.

`runs/20260829T145016Z-w35b-3way`, a+b, 30 runs and 5 warmups per row, D-1a
clean at both ends (idle 89.16 % → 87.73 %, busiest process 10.6 % → 9.3 %).
Every row is inside a single window, so no two are separated by host drift.

| `t1_head` | 353.941 | 346.836–372.591 | 26.841 | 330.786 | — |
| `t1_d4` | 352.622 | 343.465–358.638 | 26.691 | 326.509 | — |

The ordering does not cohere. d4 contains every d2 change and reads a
millisecond worse than d2. d1 and d3 both read worse than the unchanged HEAD
they were built from — and d3 is a pure alignment change, which can remove
false sharing but cannot create 1.7 ms of work. That pattern is what a set of
no-effect changes looks like once run-to-run variation exceeds all of them.

## What the harness resolves

HEAD's own pool-overhead figure reads **11.045**, **11.595** and **12.155** in
three separate windows on the same tree and the same corpus, and the five
binaries in the single window above span **10.305 to 12.759**. Both spreads are
about ±1 ms, and they are the same size — which is the point: the variation
between binaries is not larger than the variation between windows of the same
binary.

The charter asked for the figure to fall from 11.3 ms to about 4 ms. A 7 ms
effect would have stood far outside this noise. It is not there.

## Discarded and degraded rows

One d2 group and a partial control group were taken while `fseventsd` ran at
191 % CPU and a foreign multi-agent session loaded the host; that group ended
at **48.62 % idle** against the harness's 85 % floor. Both run directories were
deleted rather than reported, and the readings they produced — which showed d2
as 42 % slower — are not evidence of anything except a busy machine.

The first before/after pair (`…143341Z-w35b-before`, `…143450Z-w35b-after`) is
kept and labelled degraded in its own `summary.md`. Both groups started near
87 % idle and ended at 81.63 % and 74.20 %, and their last two rows took the
worst part of each window. Its apparent a′ regression — 15.774 to 18.361 — is
host drift: HEAD alone read 15.774 there, against a frozen reference of 12.245.

No row was forced; `forced: false` and `rustflags_match: true` in all five
retained runs.

## The spike is not a source of a better idle protocol

The charter asked what the W0.2 spike did differently to reach 121.79 ms.
Nothing, in the scheduler: `.omc/spikes/w02-walker/src/raw.rs`, `run_deque` and
`find_task`, is the same shape as the shipped pool — the same index-0 victim
sweep, the same 32 non-decaying spins, the same 500 µs park, the same
`notify_all`. The spike's advantage lies somewhere else, and the residual
analysis in the Phase-3 doc already lists the candidates.

## Conclusion

The pool's own scheduling code is not where the four-thread user CPU goes. The
metric that named it — `user@N − user@1` — charges to "the pool" everything
that differs between one thread and four, including memory-system contention
and stalls the kernel bills as user time, and the pool's scheduling code is
measurably a rounding error inside it.

W3.5b closes with no code change. `#21d` is a measured negative.

Follow-ups: the causal claims in `2026-08-29-phase-3.md` and in the plan's
W5.1 item are corrected to point here; and W3.5c profiles the `N` = 4 walk
before anything else is attempted, because a sampling profiler would have said
in one run what four rebuilds could not.
