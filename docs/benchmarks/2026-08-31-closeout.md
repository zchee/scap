# Phase 5 closeout — the post-optimisation numbers (W5.1)

Measurement record for the plan's closeout wave (plan §6 Phase 5 W5.1, ledger
`#31`). It reports what `scap` measures today against every preserved binary
of the phases that produced it.

**This is a record, not a re-gate.** No earlier phase's verdict is re-derived
here, no §9 bound is evaluated, and nothing below is a criterion. Where a
frozen absolute is quoted it is reported beside a same-window ratio and never
gated alone — the treatment deviation D-9 established.

Every timed row was taken by `scripts/bench-quiet.sh` on a machine its D-1a
gate admitted **and closed on** by itself. Since `e774820` that gate runs at
both ends of a group inside the harness; five completed groups were discarded
by it during this wave and every one is disclosed in
[Refusals and discards](#refusals-and-discards) with its numbers.
`SCAP_BENCH_FORCE` was used for exactly one group, the loaded-machine row it
exists for. `SCAP_BENCH_ALLOW_FLAGS` was used for exactly one group, the
clean-flags row set that is defined by not being under the frozen flags.

## How to read these numbers

Three properties of this host shape every table below, and each is measured
here rather than asserted.

**Absolutes have moved; ratios have not.** Today's a+b readings sit around
155 ms where the Phase-3 re-gate's pooled ensemble read 143.326 ms on
2026-08-29 — roughly 8 % slower for programs that did not change. This is the
host drift deviation D-9 recorded, which is why every comparison below is
between binaries run **in the same window**, alternating HEAD with each
reference, and why frozen absolutes are reported beside those ratios rather
than gated.

**The first timed row of a group is slower and noisier than later ones.** In
group c1, `scap --version` on HEAD read **2.865 ms** with a standard deviation
of 0.421 as the group's first row, and **2.398 ms** with a deviation of 0.064
later in the same window on the same binary — 0.467 ms apart, which is larger
than the entire 0.3 ms startup cost AC-6 was originally written to police. The
`root` rows show it too, 5.558 then 4.802. It is a measurement-order artefact.
Where it matters below, both readings are given.

**A group can drift monotonically within itself.** On corpus a, HEAD's three
interleaved readings were **130.407 / 134.121 / 136.316 ms** — a 5.9 ms spread
on a binary that could not have changed between them. This is the same effect
the Phase-3 re-gate lane found and initially misread as a real slowdown. A
single reading against a single reference on this host reports the measurement
order as much as the program, which is what the interleaving exists to expose.
HEAD figures below are pooled over its interleaved readings, and the individual
readings are printed so the spread stays visible.

## The `mimalloc` decision — NOT ADOPTED

Plan §10 expected this outcome. It is now measured rather than assumed.

**Both arms were built from the same source at the same path**, in a detached
worktree, and only one of them had the allocator. HEAD's own binary is *not*
the control: it is built at a different path, and a build path changes the
crate-metadata hash. That is not theoretical here — the control binary is
byte-size identical to HEAD at 1,818,048 B yet hashes differently
(`b7f11277…` against `92d66004…`), so measuring the variant against HEAD would
have mixed the allocator with a rebuild that ledger `#22` already recorded as
not byte-reproducible on this host. The `src/` tree on `main` was never
touched, and the worktree was removed afterwards. Neither arm is committed, so
both are pinned here and both were copied into `.omc/bench/binaries/` — the
same git-ignored durable home the reference binaries use — with `SHA256SUMS`
lines, so the pin can be checked rather than merely asserted:

| Arm | Size | sha256 |
| --- | --- | --- |
| control, system allocator | 1,818,048 B | `b7f11277f7ccf07affbc8d7f134eaf28150c9db611a4c8c8a5d7d29ed9a3f827` |
| `mimalloc` | 1,912,416 B | `f98483a8d22a701ed98e8bf3db7e325e2ff62102b65c3a716926e39264063277` |

The group's `metadata.json` records `binary_sha256` as `92d66004…`, which is
HEAD — the harness fingerprints `SCAP_BIN`, and the two arms were passed to

here and nowhere else.

| pair 2 | 0.9885 | 0.8620 | 0.9969 | 0.9882 |
| **pooled** | **0.9906** | **0.8673** | — | **0.9920** |

**`mimalloc` does what a faster allocator should — 13 % less user CPU,
consistently — and it cannot reach the bottom line, because this workload is
94 % kernel.** Pooled system time is **543.246 ms** against **32.199 ms** of
user, so the kernel holds 94.4 % of the 575.445 ms of total CPU; the allocator
cannot touch that share, and the system-time ratio confirms it at 1.00. The result is a **0.9906 wall ratio, about 1.4 ms**, which is
smaller than the 5.9 ms spread this host produced between three readings of one
unchanged binary in a single group. HEAD itself ran once in this group as
context (`mi_head_1`, 156.248 ms) and is not part of the pairing; a second HEAD
row is defined in the row file but was not selected.

Against that, adoption costs **+94,368 B** of binary (1,912,416 against
1,818,048, +5.2 %), two crates (`mimalloc`, `libmimalloc-sys`) against a
dependency budget the plan reports at every phase, and a C toolchain in the
build via `cc`. **Not adopted**, and the reason is structural rather than
marginal: the bottleneck is `readdir`, not allocation.

## The clean-flags row set (deviation D-4) — informational, never a gate

`RUSTFLAGS` unset, plain release profile, rebuilt in place, measured **beside
the frozen-regime binary in the same window** so the comparison is of flags and
not of the host. sha256 `9d6c7383de9747bef78f32b0f4654a9c603da1f14bae5fbaa7213da4901a1fe6`,
**1,818,576 B** — 528 B larger than the frozen build. `target/release/scap` was
restored to the frozen binary afterwards, so this artifact was recovered from
cargo's build cache and copied to `.omc/bench/binaries/` with a `SHA256SUMS`
line; the digest matches, which makes it the same binary rather than a claim
that the build reproduces — no fresh compile was performed. Output byte-identical on
a, b and a + b. This group is the only one where `rustflags_match` is `false`
and `allow_flags` is `true`, which is what defines it.

**These are the numbers a README may quote**, because they are what a user
building from source with no flags gets.

| Row | Clean flags | Frozen regime | Ratio | CPU ratio |
| --- | --- | --- | --- | --- |
| `--version` | 2.436 | 2.522 | 0.9661 | 0.9316 |
| `root` with `SCAP_ROOT` | 4.722 | 4.958 | 0.9524 | 0.9763 |
| `list` on a + b | 155.967 | 155.757 | 1.0013 | 1.0022 |

**The native-tuned flag regime buys nothing on the walk** — 1.0013 is parity —
and the clean build is marginally *faster* on the two startup-dominated
commands. The ordering worked against that result rather than for it: the clean
rows ran first in the group, and the first row of a group is the slow one.

This is worth stating plainly because the frozen regime is elaborate —
`target-cpu=apple-m3`, `+neon`, MIR optimisation level 4, an unroll threshold
of 500, DFA jump threading, dead stripping. On a workload that spends 94 % of
its CPU in the kernel, none of it can help, and the `[profile.release]` section
in `Cargo.toml` — `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`,
`panic = "abort"` — is already doing the work that matters. The frozen regime
remains the regime the §9 absolutes are keyed to, and nothing here changes
that; it simply is not what makes `scap` fast.

## The wall idle/imbalance probe — NOT RUN

Deviation D-9 item (a) offers an optional per-worker busy/idle accounting probe
across one a+b walk, on the condition that it uses `SCAP_LOG=debug` counters
**if they exist** and that new instrumentation is not added for it.

**They do not exist, so it was not run.** `src/walk/pool.rs` keeps no
per-worker busy or idle counters. The only busy/idle figures the debug output
carries are `tracing`'s own span timings — for corpus b, `scap::walk::root`
closes with `time.busy=26.6ms time.idle=833ns` — which measure one span's
occupancy for the whole walk, not per-worker idleness, and cannot distinguish
idle time from imbalance. Producing the probe would mean adding counters, which
this wave is explicitly not authorised to do. Recorded as not run, with the
reason, rather than approximated from a figure that does not answer the
question.

## Reproducing

Run directories, each carrying its per-row JSON, `metadata.json` and
`summary.md`: `20260831T083413Z-closeout-c1-startup`,
`20260831T083707Z-closeout-c2-ab`, `20260831T085146Z-closeout-c3-a`,
`20260831T085658Z-closeout-c4-b-aprime-depth`,
`20260831T085847Z-closeout-c7-loaded`, `20260831T090217Z-closeout-c8-mimalloc`
and `20260831T090530Z-closeout-c9-cleanflags`. The five discarded groups are
**not** committed. They were written to `/tmp/w51-discarded/` and copied to
`.omc/bench/closeout-discarded/`, which survives a reboot as the `/tmp` path
does not; the copy was verified byte-identical. **Both locations are
git-ignored, so neither can be fetched from the repository** — like the
reference binaries and their `SHA256SUMS`, they are preserved on the
measurement host only. Every gate reading is tabulated above, so the record
itself does not depend on either directory.

Row definitions: `docs/benchmarks/extra-rows-closeout.sh`, sourced by
`scripts/bench-quiet.sh` through `SCAP_BENCH_EXTRA` and selected with
`SCAP_BENCH_ROWS`. The reference binaries and the two `mimalloc` arms are not
committed; all are pinned by sha256 above.

**Two groups ran outside the default conditions, and both are recorded in
their own sections above.** The clean-flags set ran with
**`SCAP_BENCH_ALLOW_FLAGS=1`**, because it is defined by not being under the
frozen flags — its `metadata.json` reads `rustflags: ""`,
`rustflags_match: false`, `allow_flags: true`, and it is the only one of the
seven that does. The `mimalloc` arms were built in a **detached worktree**
(`git worktree add --detach`) so that `src/` on `main` was never touched, both
arms at the same path so the allocator is the only difference between them; the
worktree was removed afterwards and neither binary is committed. The
loaded-machine group is the one use of **`SCAP_BENCH_FORCE=1`**, which records
the closing gate without enforcing it — `checked: false, passed: null` — since
gating a deliberately loaded host on quiet would gate away the measurement.

**The mechanical checks.** All three ran through
`scripts/bench-doc-check.py`: every figure recomputed from the committed run
JSON and diffed against the literal strings in the text, a table-column
census, and a check that every backticked literal appears in the working tree.
The latter two exist because the Phase-4b gate lane's handoff recorded that
recomputing from JSON catches numeric errors *only*, and that the two defects
its critic caught were of neither kind.

Of 371 figures, **268 are reproduced from the run JSON** and a further **78
are checked at low precision**; the 25 that are not fall into the classes
named below, and most of them are the discard table's own gate readings. The
census reports **17 tables and 99 rows**, every row matching its header.

Those first two counts were a single count of 346 until the W5.3 review,
which found the recompute guard grading every match alike however few
decimal places it was made at. A figure printed to one decimal place is
matched against a table of tens of thousands of derived values, and on this
document's seven run groups a random millisecond value in the 0–300 range
lands on one of them 64 % of the time at one decimal place and 20 % at two,
against under 4 % at three and under 1 % at four. The guard now reports a
match below three decimals as *checked at low precision* rather than
counting it as reproduction, and prints how many distinct computations reach
each reproduced figure — 109 of the 268 are reached by more than one, and
the most contested by fourteen. **No figure changed verdict**: the 25 that
the guard could not reproduce are the same 25, and the 78 reclassified
figures are the 1- and 2-decimal ones that were previously folded into the
346. The same reclassification on `2026-08-29-phase-4b.md` turns its 243
into 172 reproduced plus 71 checked at low precision, again with its 27
unreproduced figures unchanged.

The literal check classifies **85 tokens, verifies 82 and reports 3**. All
nine binary fingerprints resolve against `.omc/bench/binaries/SHA256SUMS`, and
every abbreviated digest resolves against the full form written out in this
document, so a mistyped prefix fails rather than reading as prose. The guard
deliberately does **not** accept a full-length digest on the authority of the
document containing it: that would be self-matching, and no fabricated value
could ever fail it. The three it reports are therefore the three full **stdout
digests** — of corpus a and a′, of b, and of a + b. They are digests of listing
*output* rather than of any file, so no working tree can confirm them; they are
confirmed instead by re-running the binaries, which is what the byte-identity
check above did across six binaries and four corpora, and the corpus-a digest
additionally agrees with the full form recorded in the Phase-3 document.

**The recompute pass caught a real error in this document, and it is the error
the discard discipline exists to prevent.** The W1.4 `root` figure was first
written as **4.968 ms**, which is that binary's reading from
`20260831T081748Z-closeout-c1-startup` — a **discarded** group. The admitted
group's figure is **4.660 ms**, and the text now says so. Nothing else in the
document drew on a discarded group; the check that found this one is what
establishes that.

**What the guard cannot see.** The unreproduced figures fall into three
classes, none of which is a defect: readings from **discarded** groups, whose
run directories are deliberately outside the committed tree — the discard table
above is mostly this; **cross-document figures**, which come from the plan or
the Phase-3 re-gate rather than from these runs; and **ratios composed across
two groups**, such as the loaded-machine table, whose denominators are pooled
quiet readings from other groups. The guard pools repeated readings within a
group but does not compose ratios between groups. Refusals are a fourth class
in principle — a refusal removes its empty run directory and never writes a
`metadata.json` — but this document quotes no figure from one.

**A reproduced figure is not thereby a verified one, and the count should not
be read as if it were.** The guard tests membership in a large set of derived
values, so a number can match a computation that has nothing to do with what
the text claims. Two such false attributions are known here: the re-gate's
user-CPU ratio **0.9472** is matched to an unrelated `list_b` percentage
change, and the re-gate's **4.198** is matched to a `list_aprime` CPU divided
by a `depth_root_w14` CPU. Both are cross-document figures the guard should
have reported as unreproduced, and both are counted as reproduced instead. The
`--show-provenance` flag prints the computation behind every match, which is
the only way to tell a real reproduction from a coincidence; it should be used
on any figure a reader intends to rely on.
